## Scope and limitations

What this traceability shows, and what it does not:

- **In-process tests.** The tests drive the real protocol code (routers, sign and verify services, facilities) in one process, with injected clocks and a mocked or in-memory access layer. They do not send frames over the air.
- **Not the ETSI ATS.** The TTCN-3 Abstract Test Suites were not executed, and no accredited test lab was involved. A TP marked covered means a unit or integration test asserts the behaviour the TP checks.
- **Interoperability.** Python and Rust verify each other's frozen signed messages and certificate chains, and the implicit-certificate construction is checked against ETSI `itscertgen`'s formulas. Tests against third-party stacks (the kind done at an ETSI Plugtest) are not part of this matrix.
- **DCC.** See [DCC](#dcc): unit tests against the base standards, no TSS&TP.
- **Hardware-dependent behaviour.** The C-V2X link layer (`cv2x` feature) needs the vendor library and was not built or tested here; the TP below marked *not implemented* for C-V2X needs it.
- **PICS.** N/A means outside the PICS of these implementations (vehicle ITS-S profile, CAM v2, the forwarding algorithms of TS 103 836-4-1 V2.2.1). Optional features listed as not implemented are left out of the PICS.
- **Permutations.** A TP with a permutation table is one test that covers every permutation (signing on NIST P-256, brainpoolP256r1 and brainpoolP384r1; region kinds); the note lists them.
