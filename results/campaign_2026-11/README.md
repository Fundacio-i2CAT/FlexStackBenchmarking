# Benchmark campaign 2026-11 (raw data of the paper)

Raw results of the benchmark campaign reported in the revised V2X FlexStack
paper, run on 23–25 November 2026 on six hardware configurations, for four
implementations: FlexStack Python on CPython and on PyPy (`v2xflexstack`
0.12.0, PyPI), FlexStack Rust (`rustflexstack` 0.4.0, crates.io) and Vanetza
(commit `3b9a54446685979f467aefbeaaf6065c3c7dd902`, harness in `../../vanetza/`).

Nothing has been removed: every run that was started is in these files,
including runs flagged as outliers or thermally affected (see
[Known issues](#known-issues)). Attempts that were stopped and repeated are in
`excluded/`, with the reason. The only edit after the campaign: in the text
sidecars (`*_env.txt`, `*_MANIFEST.txt`, logs, scripts), user names, home
directories, host names, LAN IP addresses, hardware MAC addresses and
MAC-derived interface names were replaced by the placeholders `<user>`,
`<host>`, `<ip>`, `<mac>` and `<iface>`. The results CSVs and every
measured value are as written by the harness; `SHA256SUMS` is of the
published files.

How to check, re-analyse or re-run: [`../../REPRODUCING.md`](../../REPRODUCING.md).

## Layout

```
campaign_2026-11/
├── README.md           this file
├── platforms.csv       host folder -> platform label used in the analysis
├── SHA256SUMS          checksums of every file under raw/, excluded/, artefacts/ and rx_sender/
├── superseded.csv      cells measured again: the rows they replace (known issues 7 and 12)
├── summary.csv         per-cell statistics, regenerated by analysis/analyze_results.py --campaign
├── raw/<host>/         one folder per host, files exactly as written by the harness
├── artefacts/          every measured binary (Rust, Cohda MK6, Vanetza), the certificate chain, MANIFEST.txt
├── rx_sender/          sender side of the RX cells: counters, sender output, orchestration scripts and logs
└── excluded/           stopped attempts, not used in the paper
```

Per host folder:

| File | Content |
|---|---|
| `results_<platform>_<UTC start>.csv` | main campaign: one row per run |
| `results_<platform>_after_<UTC start>.csv` | cells run afterwards by `scripts/run_after.sh` (Vanetza on every host; on the RPi3 also the TX and encode cells, see below) |
| `*_thermal.csv` | per run: temperature, CPU frequency and throttling state before and after the run |
| `*_env.txt` | host, kernel, OS, board, online CPUs, governor and frequency of the pinned cores, swap, software versions and binary hashes, running services |
| `*_MANIFEST.txt` | the campaign artefacts: FlexStack wheel SHA-256, rustflexstack crates.io checksum, harness commit and hash of uncommitted changes, SHA-256 of the Rust binaries and of the certificate chain |
| `bench_run_<UTC start>.sh` | the exact script the host executed for the main campaign (generated by `ansible/run.yml`) |
| `bench_run.log`, `run_after_<UTC start>.log` | console output of the main campaign and of the follow-up runner |

|---|---|---|
| `laptop` | `laptop` | Dell Latitude 5420, Intel Core i7-1185G7, OEM 15 W configuration, turbo disabled: 1.8 GHz |
| `rpi5` | `rpi5` | Raspberry Pi 5, BCM2712, 4 × Cortex-A76 at 2.4 GHz, 8 GiB |
| `rpi3` | `rpi3` | Raspberry Pi 3 Model B Rev 1.2, 4 × Cortex-A53 at 1.2 GHz, 64-bit OS |
| `agx-orin-50w` | `agx-orin-50w` | NVIDIA Jetson AGX Orin Developer Kit (64 GiB), power mode MODE_50W: 12 cores online, 1.498 GHz |
| `agx-orin-30w` | `agx-orin-30w` | the same board model, power mode MODE_30W: 8 cores online, 1.728 GHz |

The CSVs of both AGX boards say `platform = agx-orin` and those of the Nanos
`orin-nano`; the analysis takes the label from `platforms.csv`, so the two AGX
power modes are never pooled. Exact kernel, OS and interpreter versions are in
each `*_env.txt` (the Jetsons run CPython 3.12.3, L4T R39.2.1).

## Protocol

Identical on every host (see the `bench_run_*.sh` scripts):

- Benchmark process pinned to cores 2 and 3 (`taskset -c 2,3`) at real-time
  round-robin priority 50 (`chrt -r 50`); governor `performance`, swap off,
  non-essential services stopped (`scripts/prepare_system.sh`).
- Saturated cells (`target_rate` 0): 30 runs of 60 s. Fixed-rate cells
  (`target_rate` 10, 100 or 1000 msg/s): 10 runs of 60 s.
- Warm-up 5 s before each run (15 s for PyPy), cool-down 10 s after it;
  each run is bounded by `timeout -k 10 (60 + warm-up + 120)` s.

## Columns

`results_*.csv`, one row per run:

| Column | Unit | Meaning |
|---|---|---|
| `run_id` | | run number within the cell (1..30 or 1..10) |
| `implementation` | | `cpython_<ver>`, `pypy_<ver>`, `rust`, `vanetza` |
| `platform` | | as written by the harness (see Platforms) |
| `security` | | `on`: TS 103 097 signed; `off`: unsecured |
| `benchmark` | | `codec-encode`, `codec-decode`, `security-sign`, `security-verify`, `tx` (`rx` in the RX files); what is timed: table *Measurement boundary* of the paper and `../../vanetza/README.md` |
| `duration_s` | s | measured duration |
| `total_cams` | | operations completed in the measurement phase |
| `throughput_cams_s` | 1/s | `total_cams / duration_s` |
| `latency_mean_us` … `latency_max_us` | µs | per-operation time over all operations of the run: mean, std, p50, p95, p99, min, max |
| `sign_latency_mean_us` | µs | mean signing time inside `tx` with security on (empty otherwise) |
| `cpu_pct` | % | process (user + system) CPU time over wall time; 100 % = one core |
| `rss_start_mb`, `peak_rss_mb` | MiB | resident memory after initialisation and at its peak (the peak includes the latency samples the harness keeps) |
| `target_rate` | 1/s | 0 = as fast as possible; otherwise the paced rate |

`*_thermal.csv`, one row per run (the analysis joins it to the results per
run): `start_utc`, `end_utc`, `temp_start_c`, `temp_end_c`,
`freq_start_khz`, `freq_end_khz` (first pinned core), `throttle_start`,
`throttle_end` (Raspberry Pi: `vcgencmd get_throttled` bit field; x86: summed
`core_throttle_count` of the pinned cores; empty on the Jetsons).

## Known issues

1. **RPi3 frequency capping.** The board reached 80–84 °C in the saturated
   Rust TX (all 30 runs of both cells), PyPy TX (22/30 runs of each cell) and
   PyPy encode (25/30) cells and hit its soft temperature limit
   (`throttle_*` bit 0x2 "ARM frequency capped", sticky bit 0x20000 set from
   then on). Capped PyPy TX runs are about 6 % and capped PyPy encode runs
   about 11 % slower than the uncapped runs of the same cell. All other cells,
   including every CPython, decode, sign and verify cell, ran uncapped. The
   rows are kept and the flag is in the thermal file.
2. **The two AGX Orin boards use different power modes** (above). Their
   throughput differs by the clock ratio (1.15–1.18 against 1.154) in every
   cell; they are reported as two configurations, not as replicates.
3. **CPU frequency in the thermal files is sampled between runs**, when the
   cores are idle; on the laptop it therefore reads 0.4–1.8 GHz. Sampled
   during a run, the busy pinned core holds 1.8 GHz.
4. **PyPy shutdown error on the laptop.** In 10 runs of the PyPy unsecured TX
   cell, `bench_run.log` shows a traceback from the GeoNetworking beacon
   timer, `OSError: [Errno 9] Bad file descriptor` (in one of them the process
   exited before the traceback was printed in full): the stack closed the
   socket while the timer thread was still sending, after the run had been
   measured and written. No run failed and no row is missing.
5. **Two versions of `scripts/run_after.sh`** ran: the Jetsons, laptop and
   RPi5 used the first one (Vanetza and Rust cells); the RPi3 used the current
   one, which adds CPython and PyPy cells. Vanetza and Rust cells are run
   identically by both.
6. **Interpreter versions differ across platforms** (CPython 3.12 on the
   Jetsons, see `*_env.txt`); the implementation column carries the version.
7. **Rust TX cells re-run (superseded rows).** The first Rust harness
   flooded the stack during the warm-up (no wait for each packet), and the
   200 ms pause before the window did not drain the queues: in the secured
   cells the signer was still working through warm-up packets during the
   whole measurement, so in the secured 10 msg/s cell the CPU read ~100 %
   and the latency was the wait for the next queued packet (RPi5 p50 210 µs
   against a 416 µs signature); the saturated cells were affected less
   (secured: latency without the encode and GeoNetworking part; unsecured:
   the first seconds of each run). The harness now warms up with the same
   closed loop as the measurement and waits until the stack is idle
   (`pacing::wait_quiescent`), and the four Rust TX cells (`tx` off/on, max
   rate and 10 msg/s) were run again on every host with
   `scripts/run_after.sh`. `superseded.csv` names the rerun file per host;
   the analysis drops the Rust `tx` rows of the other files of that host. The
   original rows stay in the raw files. Binary of the rerun:
   `artefacts/bin/rerun_rust_tx/`. Python and Vanetza send synchronously and
   were not affected. On the RPi3 (board b, 13:00–14:40 UTC) run 14 of the
   unsecured saturated cell (13:16:46–13:17:51 UTC) overlapped a 13 s
   broadcast flood of the Ethernet RX sender (13:17:12–13:17:25 UTC),
   started by mistake while board b was still on the same switch; it is the
   lowest run of the cell (7,390 CAMs/s against a mean of 7,453, z = −4.0)
   and is kept (without it the mean changes by 0.03 %). The rerun ran at
   46–57 °C without frequency capping, unlike the original RPi3 Rust TX
   cells (known issue 1).
8. **Real-time bandwidth limit.** The kernels keep the default
   `sched_rt_runtime_us` = 950000 (of 1000000): a thread at real-time
   priority runs at most 950 ms per second on a CPU. On the laptop and the
   Jetsons, every saturated single-threaded cell reads 95 % CPU and its
   throughput × mean latency is ≈ 1.0, i.e. the process was stopped 5 % of
   the wall time; on the RPi5 the same cells read 100 %. Single-threaded
   capacities on the laptop and the Jetsons are therefore ~5 % below the
   capacity of the core, equally for every implementation, and the 50 ms
   stall shows in the p99 of the slowest operation (Python verification,
   e.g. 57 ms against a 10.5 ms p50 on the AGX Orin 50 W). Recorded on the
   AGX Orin: 950000; not recorded per run in `*_env.txt`.
9. **Vanetza harness memory grows by ~160 bytes per message sent** (peak
   minus start of a saturated TX run over the number of messages, laptop and
   RPi5), also during the warm-up; `rss_start_mb` of its TX cells therefore
   includes ~50 MB (unsecured) retained from the 5 s warm-up. Its codec and
   sign cells (7–12 MB) show the footprint without this.

10. **RPi5 swap is a zram device.** `prepare_system.sh` runs `swapoff -a`, but the
    RPi5 records one active swap device in every `*_env.txt` (campaign and
    rerun): Raspberry Pi OS's compressed-RAM swap (`/dev/zram0`, 2 GiB), with
    0 bytes used (checked after the rerun). No swapping to storage took place.

11. **Cohda MK6 (`raw/mk6-101`, `raw/mk6-107`, run 2026-11-25).** Harness
    `flexstack-bench-cv2x` (`rust/src/bench_cv2x.rs`, feature `cv2x`), built for
    the three firmware variants with `scripts/build_cv2x_variants.sh`
    (`artefacts/bin/mk6/`); both units are the `mk6-fw19` variant. The TX path
    now hands each packet to the C-V2X link layer over a zero-capacity channel,
    so a packet counts as sent once the link-layer thread has taken it (after
    the previous modem send) and no queue forms in front of the modem; TX
    throughput is the rate handed to the radio API, not the over-the-air rate
    (a second unit received ~1.3 k CAMs/s at 11 % CPU while 4.6 k/s were sent).
    The modem accepted every send (no `Send error` in the logs). MK6 RX over
    the air: known issue 13. While Wi-Fi was being configured as
    a control network (12:40-12:48 UTC), background `wpa_supplicant`/`dhclient`
    activity overlapped runs 7-10 of `security-verify` at 100 msg/s and runs
    1-3 at 1 000 msg/s on unit 101, and runs 27-30 of `security-sign` and 1-4
    of `security-verify` on unit 107; their values lie within the spread of
    the other runs of each cell, and they are kept. The 560 `error 0` lines in
    the MK6 logs are status messages of the Telux library, not errors.

12. **Ethernet RX cells (`raw/laptop`, `raw/rpi5`, `raw/rpi3-a`, run
    2026-11-25).** The three receivers ran the RX cells of the four
    implementations at the same time, receiving the same frames from one
    sender: a separate x86 computer on the same switch, running the Vanetza
    harness (`--mode tx`, commit above) in Docker, as three slots that each
    run 60 s chunks back to back, staggered by 20 s (a long-running Vanetza
    sender runs out of memory, known issue 9). The switch was disconnected
    from the router during the RX cells, and the wired ports of the sender
    and receivers had no IP address (`nmcli ... ipv4.method disabled`), so
    the data plane carried only the benchmark frames; the receivers were
    controlled over 2.4 GHz Wi-Fi. The sender's interface counters
    (`rx_sender/sender_counters.csv`) give 100,330 frames/s unsecured,
    9,487 signed frames/s secured and 100,145 frames/s in the rerun below,
    averaged over each phase. A cell whose throughput is at the sender rate
    (Rust and Vanetza unsecured on the laptop and the RPi5) measures the
    sender, not the receiver: it is a lower bound of the receiver's
    capacity. The `sender_*.csv` files in `rx_sender/` are the sender's own
    harness output (its `--platform` argument says `laptop`; they are not
    read by the analysis).

    Two harness defects showed up in the unsecured phase and were fixed in
    `python/benchmark.py` before the secured phase:
    - the Python RX cell read the latency list while the receive thread was
      still appending to it after the 60 s window; PyPy then failed in
      `np.array` ("Content of sequences changed"), losing 20/30 runs on the
      laptop and 7/30 on the RPi5 (CPython included a few samples after the
      window). The window's count and latencies are now taken under the
      lock at its end, as the Rust harness does;
    - the Python harness wrote CSV lines ending in `\r\n`; the Vanetza
      harness compares the header byte for byte and refused to append to
      the files created by the CPython cell, so the first unsecured Vanetza
      RX cell wrote no rows (its 30 attempts per host are in the
      `run_after_20261125T145831.log` files). It now writes `\n`, as the
      Rust and Vanetza harnesses do.

    Both unsecured cells, PyPy and Vanetza, were then run again on all three
    receivers (`results_*_after_20261125T2015*/T2115*`); `superseded.csv`
    replaces the earlier unsecured PyPy rows (security column `off`). The
    surviving earlier PyPy runs agree with the rerun (laptop 38,086 against
    37,932/s, RPi5 23,194 against 23,478/s). The 35, 18 and 30
    `Bad file descriptor` tracebacks (laptop, RPi5, RPi3 a) in the Python logs come from the
    beacon timer of the unsecured MIB sending after the socket is closed, at
    the end of a run whose row is already written; no run failed.

    RPi3 board a (`raw/rpi3-a`; no heatsink) reported no under-voltage, but
    reached 80–85 °C and was frequency-capped (`throttle_*` bit 0x2) in
    25/30 CPython, 30/30 Rust, 30/30 Vanetza and 30/30 (rerun 28/30) PyPy
    unsecured runs and in 5/30 PyPy secured runs. The thermal file reads
    1.2 GHz throughout (known issue 3); `vcgencmd measure_clock arm` during
    the unsecured cells read 0.93–1.2 GHz. Its RPi3 RX results are
    throttled values. The Rust receiver on the RPi3 processes ~10 k of the
    ~100 k frames/s: the excess queues in RustFlexStack's unbounded
    link-layer channel, so latency (mean ~20 s) and peak RSS (~468 MB) in
    the unsecured Rust RX cell measure that backlog; its throughput is the
    receiver's processing rate. The C receivers and the Python receivers
    drop the excess in the kernel socket buffer instead.

13. **Cohda MK6 RX over the air (`raw/mk6-107`, run 2026-11-25).** Unit 101
    sent saturated CAMs over C-V2X in one continuous 2,700 s process per
    security mode (`rx_sender/mk6_ota_rx.sh`; its output
    `raw/mk6-101/ota_sender_*`, not read by the analysis: 4,705 CAMs/s
    unsecured and 478 CAMs/s secured handed to the radio API, no send
    errors) while unit 107 ran the 30 RX runs. Unit 107 received 1,507 CAMs/s
    unsecured at 18.5 % CPU and 101 CAMs/s secured at 33 % CPU, with no
    errors; the radio delivered ~110 secured frames/s, so both cells measure
    the radio link, not the receiver. The radio frame counter of each run
    also counts the 5 s warm-up, so it exceeds the CAMs delivered in the
    60 s window by about the warm-up's packets.

## Excluded attempts (`excluded/`)

- `undervoltage_rpi3-a`, `undervoltage_rpi3-b`: first RPi3 attempts on two
  boards that reported under-voltage (`get_throttled` 0x50005 and 0x50000).
  Board b was stopped, got a new power adapter and ran the campaign above;
  board a was stopped then, and later ran only the Ethernet RX cells
  (known issue 12) with a different power supply, without under-voltage.
- `rx_sender_oom_laptop`, `rx_sender_oom_rpi5`, `rx_sender_oom_rpi3-a`: the
  first Ethernet RX attempts (2026-11-25, 13:25–13:56 UTC; the laptop and
  RPi5 file names are in local time, UTC+1). In the first two the receivers
  still had an older `run_after.sh` without the CPython and PyPy cells
  (`unsupported impl`); they were stopped after the first Rust run and the
  current script was deployed. In the third the sender ran as long-running
  processes, which ran out of memory after about 8 runs (known issue 9):
  the later runs received nothing (throughput 0). All three were stopped
  and the RX cells repeated from the start with the rolling sender (known
  issue 12).

The pre-release campaigns of April and June 2026 (older stack versions) are
in `../archive/`; they are not used in the revised paper.
